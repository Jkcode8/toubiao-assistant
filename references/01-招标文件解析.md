# 招标文件解析规范

来源：成熟桌面端投标工具的 18 个解析任务与提示词口径。
解析的目标不是"读懂招标文件"，而是产出**可直接驱动目录、正文、废标自查的结构化事实**。

## 一、通用输出纪律

所有解析任务共用同一段系统约束：

1. 严格基于招标文件原文，优先使用原文内容，不自行编造。
2. 已提取到相关内容但局部信息没提及，明确写"没有提及"。
3. 只输出最终结果，不输出过程、提示语或客套话。
4. 始终使用简体中文。

Markdown 类任务额外约定：**整项完全无结果时只返回"未提取到"**，不加标题、标点、解释；
只要提取到任何有效内容就正常返回，局部缺失写"没有提及"。
返回"未提取到"时**必须整项重跑一次**再判定（工程实践：首次为"未提取到"则完整重跑，第二次结果原样采用）。
JSON 类任务：只输出 JSON，只改 value，不改 key 与结构，招标文件没有的字段填"没有提及"。

## 二、18 个解析项

| # | id | 名称 | 必填 | 输出 | 提取要点 |
|---|---|---|---|---|---|
| 1 | projectOverview | 项目概述 | 是 | MD | 项目名称、基本信息、背景目的、规模预算、时间安排、实施内容、技术特点；只要与项目实施有关，不提取商务信息 |
| 2 | techRequirements | 技术评分要求 | 是 | MD | 技术评分项与技术评分要求分开（见第三节） |
| 3 | projectInfo | 项目信息 | 是 | JSON | 名称/编号/类型/预算/地址 |
| 4 | partAInfo | 甲方信息 | 是 | JSON | 公司名称、地址、联系人、电话 |
| 5 | deliveryAndServiceRequirements | 交货和服务要求 | 是 | JSON | 实施周期、交付范围与地点、验收、质保、售后、响应时限、培训、文档交付 |
| 6 | procurementList | 采购清单 | 否 | MD | 采购内容/需求/货物需求/服务内容/技术参数/规格/报价清单/工程量清单 |
| 7 | responseFileRequirements | 响应文件要求 | 是 | MD | 文件组成、固定格式模板、签章、命名、装订密封、份数、递交截止、递交方式 |
| 8 | agentInfo | 代理机构信息 | 否 | JSON | 机构名称地址联系人电话邮箱、银行账户四要素 |
| 9 | keyInfo | 投标关键节点 | 否 | JSON | 公告发布、文件获取方式/售价/时间、提交地点、投标截止、开标时间地点 |
| 10 | marginInfo | 投标保证金 | 否 | JSON | 金额、缴纳方式、截止、退还条件、不予退还情形 |
| 11 | qualificationReview | 资格性审查 | 否 | MD | 投标人资格条件与审查要求（表格转列表） |
| 12 | complianceCheck | 符合性检查 | 否 | MD | 文件完整性/有效性/规范性/偏差处理 |
| 13 | openBid | 开标要求 | 否 | JSON | 时间地点、参与要求、无效标认定、异议处理、开标流程 |
| 14 | evaluationBid | 评标要求 | 否 | JSON | 评标委员会组成与职责、评分构成、评标方法、原则与细则 |
| 15 | businessScoring | 商务评分要求 | 否 | MD | 商务评分因素（为商务方案准备） |
| 16 | discardedBids | 无效标与废标项 | 否 | MD | 见第四节，**决定废标自查清单** |
| 17 | signingProcess | 合同授予与签订 | 否 | JSON | 中标公示、合同签订、履约保证金、合同文本 |
| 18 | terminationCondition | 合同解除和终止 | 否 | JSON | 违约解除、不可抗力、合同终止、争议解决 |

必填 6 项（key 模式）：projectOverview、techRequirements、projectInfo、partAInfo、
deliveryAndServiceRequirements、responseFileRequirements。
其余 12 项为 full / custom 模式按需勾选，**必填项永远不会被取消**。

必填项的 JSON 键（只改 value，不改 key）：

```json
// projectInfo
{"project_name":"","project_number":"","project_type":"","project_budget":"","project_address":""}
// partAInfo
{"company_name":"","address":"","contact_person":"","contact_phone":""}
// deliveryAndServiceRequirements
{"implementation_period":"","delivery_scope":"","delivery_location":"","acceptance_requirements":"",
 "warranty_period":"","after_sales_service":"","response_time":"","training_requirements":"",
 "documentation_requirements":""}
```

## 三、技术评分项 vs 技术评分要求（最容易做错的一步）

识别范围：技术评分、评标方法、评分标准、技术参数、技术要求、技术方案、技术部分、评审要素。
排除商务、价格、资质条目。

- **技术评分项**：投标人需要在技术方案中一一响应、展开编写，并能形成方案章节的具体评分内容
  （方案类、措施类、团队类、实施类、服务类、保障类、运维类、应急类、检查类）。
- **技术评分要求**：约束评分、解释评分、定义扣分或判定规则的通用规则
  （符合性要求、偏离扣分规则、判定口径、适用范围说明、表后说明、通用评审规则）。

判断依据：**该内容是否要求投标人在技术方案中展开具体方案内容**。不是具体方案内容，
即使带分值或扣分规则，也归入技术评分要求。原文有层级关系时保持顺序与来源，不自行合并。

输出格式：

```
## 技术评分项

【评分项名称】：<原文描述，保留专业术语>
【权重/分值】：<具体分值或占比>
【评分标准】：<详细规则>
【数据来源】：<章节、条款、页码或表格位置>

## 技术评分要求

【评分要求名称】：
【适用范围】：
【要求/判定口径】：
【数据来源】：
```

某类无内容时保留标题并写"没有提及"。

## 四、无效投标与废标项的概念边界

- **无效投标**：投标人、投标文件、签章密封、递交时间、报价、保证金、资格条件、实质性响应等原因，
  导致投标被认定无效、否决、不予受理或按无效响应处理的情形。
- **废标项**：可能导致项目废标、采购失败、重新招标、终止评审、有效投标人不足或实质性响应不足的条款或风险项。
- 同义表达一并归类：否决投标、投标无效、不予受理、无效响应、重大偏差、实质性偏离、废标情形。

输出的两段结构固定：

```
# 招标文件中明确提到的
## 无效投标
## 废标项
# 此类标书还可能涉及的
## 无效投标
## 废标项
```

- 前者只提取原文明确出现或同义表达的内容，尽量保留关键句；没有则写"招标文件未提及"。
- 后者按经验补充高风险遗漏项，但**每个小节最多 3-5 条**，不罗列通用清单、不写泛泛之谈。

## 五、其他解析要点

- **采购清单**：优先保留原文表格与字段含义；原文是表格则整理为 Markdown 表格；多章分散描述时合并整理，
  但不得编造不存在的字段；无明确清单时说明"未找到明确采购清单"并列出相关段落摘要。
- **响应文件要求**：按招标文件实际结构整理，不套固定模板；保持投标文件所列顺序，便于后续一一对应编写；
  区分"必须提供"与"如适用/可选"；不生成供应商响应文件、不编造公司信息与报价。
- **分段处理**：超长招标文件按上下文上限切段解析，再合并为一份结果；合并时以原任务要求为准，
  不得因分段产生重复条目。
- **多标段**：若招标文件分标段，先识别标段并确认本次投标范围，再对所选标段范围内解析；
  未选定标段时不得开始解析。

## 六、解析结果的使用方式

| 解析产物 | 下游用途 |
|---|---|
| projectOverview | 项目概述章节、正文项目背景提示 |
| techRequirements | 评分项结构化 → 目录规划、评分响应对照表 |
| responseFileRequirements | 投标文件整体目录结构（不只是技术标） |
| discardedBids | 废标自查清单（见 04-质量检查规则） |
| deliveryAndServiceRequirements | 工期、验收、质保、售后章节的事实口径 |
| keyInfo / marginInfo | 投标日程与保证金核对 |
| qualificationReview / complianceCheck | 资格与符合性自查 |
