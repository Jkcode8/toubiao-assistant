# 目录生成规则

来源：成熟桌面端投标工具的目录生成链路。目录不是"写得好不好看"的问题，
而是**评分项能不能被逐条命中**的结构保障。以下规则为硬约束。

## 一、节点模型

```json
{
  "id": "稳定 UUID，新节点填 null 由程序分配",
  "number": "按树位置计算的显示编号，不写入 id",
  "title": "纯标题，不含「第一章」「1.1」「附件1」等编号前缀",
  "description": "目录说明",
  "attr": "仅一级目录有：通用 / 商务/资信 / 技术 / 其他 / 目录 / 报价 / 业绩",
  "children": "父节点才有，至少 2 个",
  "content_mode": "仅叶子有：ai-generate / template-fill / directory-generate / manual-fill / other",
  "content_mode_note": "仅 content_mode=other 时说明原因"
}
```

硬规则：

1. 父节点**只含 children，不含 content_mode**；叶子**只含 content_mode，不含 children**。
2. 任意非叶子节点 children **至少 2 个**，禁止"只有一个子节点"的冗余层级。
3. 最多六级。
4. `id` 是身份，`number` 是显示编号；已确认节点的 id 在改名、排序、层级变化时**保持不变**。
5. `title` 只写纯标题，不含 Markdown 标记与章节编号。

## 二、属性与处理模式的对应

| attr | content_mode | 含义 |
|---|---|---|
| 技术 | ai-generate | AI 生成正文 |
| 商务/资信 | template-fill | 用招标文件抽出的模板填写 |
| 业绩 | template-fill | 同上 |
| 目录 | directory-generate | 目录页由程序按最终目录生成 |
| 报价 | manual-fill | 人工填写，不生成 |
| 通用 / 其他 | 按内容判断，特殊用 other + 说明 | —— |

只有 `ai-generate` 参与正文生成与配图、字数统计。不得为了凑数量把 template-fill /
directory-generate / manual-fill 改成 ai-generate。

## 三、四阶段流程

### 阶段 1：一级目录

- 目的：确定整本响应文件（或单独装订的技术文件）的一级结构。
- 技术文件独立成册时：**每个一级目录直接对应一个技术评分大项**，保持评分大项原顺序与正式表述；
  不得创建"技术方案""施工组织设计""技术标""监理大纲"等外层总目录，也不得混入商务/资信、投标函、授权委托书。
- 完整投标文件时：一级目录按响应文件实际组成确定，技术方案作为其中一个分支（attr=技术）。
- 生成后**必须经用户确认**一级目录数量、顺序、标题、属性，才能进入下一阶段。

### 阶段 2：评分项结构化与目录规划

1. 只从"技术评分项"提取，**技术评分要求不得提取为评分项**（它只作为评分标准与编写约束）。
2. 评分大项写入结构化清单，编号 R1、R2…，保持原顺序、专业术语与关键评分细项：

```json
{"groups":[{"requirement_id":"R1","title":"评分大项","description":"关注内容","detail_points":["关键评分细项"]}]}
```

3. 建立"评分项 → 目录位置"映射（`score_item_level` 为该分支内评分项应处的层级，
   不同分支可以不同，不预设必须是二级）：

```json
{"branches":[{"root_id":"根节点ID","root_title":"技术方案","score_item_level":2,
  "mappings":[{"requirement_id":"R1","target_title":"评分大项目录标题"}]}],
 "extra_titles":[],"allow_root_changes":false}
```

4. 每个 requirement_id 在 mappings 中**恰好出现一次**；默认一一对应。
   合并（多个 mapping 同 target_title）、拆分（additional_titles）、新增同层级大项
   **必须经用户批准**，并在 adjustment_note 记录。
5. 以下偏离必须向用户确认：合并/拆分评分项、遗漏评分项对应节点、新增评分项之外的同层级大项、
   改变评分项目标层级、增删改一级目录。普通标题规范化、下级目录扩展不需要询问。
6. 一级目录默认锁定（`allow_root_changes=false`）。

### 阶段 3：叶子数量分配 + 生成完整目录

- 叶子数量目标来自字数控制：有上下限时以中点为基准，仅有下限取 120%，仅有上限取 80%；
  再由 Agent 按"每节目标字数"折算 AI 叶子数。未设置字数目标时由 Agent 按项目复杂度判断。
- 分配规则：每个技术分支**至少 2 个**（独立成册模式下允许 1 个，表示保留该一级目录本身作为叶子）；
  所有 leaf_count 之和必须等于可分配叶子总数；禁止用 1~2 个残次分支凑数。
- 生成时：
  - 以评分项清单为**权威清单**，以目录规划为**权威位置**；映射节点标题基本保持评分大项专业表述。
  - detail_points 用于生成评分项节点的下级目录。
  - 每个评分项形成独立节点；未见批准的 extra_titles 一律不得增加。
  - 已有节点 id 原样保留，新节点 id 为 null；数组顺序即排序。
  - 参考知识库/原方案只能用于完善评分项**下级结构**，不得改变评分映射、不得引入未批准的同层级大项。

### 阶段 4：终审（先审后改）

审核维度：

1. **叶子数量**：与目标偏差在 ±2 以内，只统计 ai-generate 叶子。
2. **评分覆盖**：直接以原始技术评分信息为依据，逐项检查是否被目录准确覆盖；
   结构化清单与规划只用于核对已确认的映射，不能掩盖原始评分信息中的遗漏。
3. **重复目录**：重复、近义、含义重叠、只换一种说法；不同专业分支下确有独立含义的同名标题不机械判重。
4. **专业合理性**：层级、颗粒度、逻辑顺序、标题表达、节点归属、处理模式是否适合正式投标文件。
5. **来源与完整性**（"仅用原方案"模式）：逐章核对原方案，不得新增原方案中不存在的章节，也不得为凑数拆分。

处理纪律：

- **必须先完整审核并形成问题清单，不得边审边改。**
- 无问题：不改目录，记录 status=passed、issues=[]。
- 仅"标题专业化"与"不涉及映射节点的明显重复合并"可静默修复（status=simple_fix）。
- 评分覆盖缺失、叶子数量越界、评分项目标层级调整、一级目录调整、增删拆分目录、跨分支移动、
  明显结构重排 —— 一律先集中询问用户，一次问清，问完不再二次询问。
- issues 的 category 只能用：leaf-count、score-coverage、duplicate-directory、professional-structure。

## 四、自检清单（生成完整目录后逐条打勾）

- [ ] 每个技术评分项在目录中有且仅有一个对应节点，标题可对上原文。
- [ ] 技术评分要求没有被做成独立章节。
- [ ] 一级目录未擅自增删改序，属性与处理模式匹配。
- [ ] 无单子节点层级、无六级以下目录、无编号写进 title。
- [ ] ai-generate 叶子数与目标偏差 ≤ 2。
- [ ] 同一父节点下无近义重复标题。
- [ ] 商务/资信、业绩、报价、目录类节点未被当作 AI 正文生成。
- [ ] 目录顺序符合评标习惯：先总体方案，再分项措施，最后保障体系。
